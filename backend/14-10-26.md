### 2. 📥 Selecting the posts

W3Schools has a select example (<https://www.w3schools.com/php/php_mysql_select.asp>).
It is not great, and it also builds an HTML table from the data, which we do not want.
The connection part we already have; the useful lines are the **query** and the
**fetch**:

- the example fetches one row at a time, but we want every row, so **`fetchAll()`**;
- it selects `id, firstname, lastname` from a `MyGuests` table that does not exist in our
  database, so those had to change (a leftover `firstname` gives an *unknown column*
  error).

Instead of listing every column, `SELECT * FROM posts` takes them all. Written with a
star, read out as "select all". Dumping the result showed an array of two elements, one
per row, each a slightly odd array (more on that in section 6).

### 3. 🧱 The connection moves into `DB`

Copy-pasting the connection and the query into every controller method that needs posts
is exactly what we do not want. There was already an empty `DB` class in `src/`, waiting
since the autoloading lesson. The plan:

- the **constructor** opens the connection, once per `DB` object;
- the connection is stored in a **private property**, `$conn`, so every `$conn` becomes
  `$this->conn`;
- the query gets its own **method**. It reads every row, so it is called `all()`, and it
  **returns** the rows instead of dumping them. What to do with them (dump them, pass
  them to a view) is the caller's decision.

`PDO` and `PDOException` are used here now, so their `use` lines move from the controller
into `DB.php`.

```php
class DB {
    private $conn;

    public function __construct(){
        $servername = "localhost:33061";
        $username = "root";
        $password = "example";
        $dbname = "learnphp";

        try {
            $this->conn = new PDO("mysql:host=$servername;dbname=$dbname", $username, $password);
            // set the PDO error mode to exception
            $this->conn->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
            
        } catch (PDOException $e) {
            echo "Connection failed: " . $e->getMessage();
        }
    }
```

The controller shrinks to an import and two lines:

```php
use App\DB;
```

```php
$db = new DB();
$posts = $db->all('posts');
```

Refresh: same two rows as before, but the controller no longer knows anything about
connections.

### 4. 👤 A `users` table

To test with more than one table, DataGrip got a second one, built with the same
decisions as `posts`:

- **`id`**: `bigint unsigned`, primary key, auto increment;
- **`name`**: `varchar(1024)`, not null. Added last, then dragged up to sit after `id`;
- **`email`**: `varchar(255)`, not null, and a **unique key**: two accounts with the same
  e-mail make no sense;
- **`password`**: `varchar(1024)`, not null. Unique? Definitely not;
- **`created_at`** and **`updated_at`**: `datetime` with the default `current_timestamp()`,
  plus **on update** for `updated_at`, so the database fills both.

The structure was exported again with **SQL Scripts > SQL Generator**, overwriting
`tables.sql`, so another classroom (or another computer) gets both tables:

```sql
create table users
(
    id         bigint unsigned auto_increment
        primary key,
    name       varchar(1024)                        not null,
    email      varchar(255)                         not null,
    password   varchar(1024)                        not null,
    created_at datetime default current_timestamp() null,
    updated_at datetime default current_timestamp() null on update current_timestamp(),
    constraint users_pk_2
        unique (email)
);
```

A few made-up users went in by hand. Remember **Submit**: until then they are not
actually in the database.

### 5. 🎯 The table becomes a parameter

Can the controller get the users through `DB` now? No: `SELECT * FROM posts` is **hard
coded** in `all()`, and nothing in `PublicController` can change it. The fix is to take
the table name as a parameter, typed as a `string`. The SQL is already in double quotes,
so the variable goes straight into it:

```php
public function all(string $table){
    $sql = "SELECT * FROM $table";
```

```php
$posts = $db->all('posts');
dump($posts);
$users = $db->all('users');
dump($users);
```

Both dumps work, and a third table would too: `all()` is now universal.

### 6. 🔢 Fetch modes

Back to the odd arrays. Each row came back with every value **twice**: once under the
column name (`id`, `title`, `body`) and once under a number (`0`, `1`, `2`). PHP allows
mixing named and numbered keys in one array, and PDO does it by default. The result
object can be told how to fetch with `setFetchMode()`, and there are several modes:

- **`PDO::FETCH_BOTH`**: the default. Both kinds of keys.
- **`PDO::FETCH_NUM`**: only the numbers.
- **`PDO::FETCH_ASSOC`**: only the column names ("assoc" for associative: key and value).
- **`PDO::FETCH_OBJ`**: not an array at all, but an object of type **`stdClass`**, with
  the columns as properties. `stdClass` means *standard class* (no, not that STD): a class
  built into PHP, mostly used for anonymous objects. Objects are a bit nicer to use, with
  arrows instead of brackets and quotes, but `stdClass` does not let us do anything more
  with the rows later.

What we really want is a class of **our own** that the database fills in.

![Fetch both](https://api.memegen.link/images/same/$post[0]/$post['id']/They're_the_same_value.png)

### 7. 🧩 Models

Classes that represent data from the database are often called **models**. They get their
own folder, `src/Models` (capital M), and are named in the **singular**: the table is
`posts` because it holds many, but one object is one row, so the class is `Post`. Same
for `users` and `User`:

```php
namespace App\Models;

class Post {
```

To fill it, the fetch mode is **`PDO::FETCH_CLASS`**. On its own that gives an error:
`setFetchMode()` expects at least two arguments in this mode, because it needs to know
**which** class. It wants the fully qualified name, which `::class` gives us (with the
leading backslash, since `DB.php` is itself in the `App` namespace):

```php
$result->setFetchMode(PDO::FETCH_CLASS, \App\Models\Post::class);
return $result->fetchAll();
```

The dump now shows objects of type `App\Models\Post`, after a wall of warnings: *Creation
of dynamic property ... is deprecated*.

**Deprecation** is a very common thing: a language or library tells you "this still works
now, but in a future version it will be changed or removed". Here PHP fills in properties
(`id`, `title`, ...) that the class never said it has. It works in PHP 8, but it may not
in PHP 9, and we want our code to be upgradeable, so we fix it. The fix is to declare the
properties, with the same names as the columns in the database:

```php
class Post {
    public $id;
    public $title;
    public $body;
    public $created_at;
    public $updated_at;
}
```

The warnings for posts are gone. The users still have them, though: `all()` fills
**every** table into `Post`, even the users. That is where we stopped (lunch was waiting),
and where we continue next time.

## ✅ Takeaways

1. **The export is structure only.** Run `tables.sql` to recreate the tables on a new
   computer, and add test rows by hand (then Submit).
2. **`query()` plus `fetchAll()`** gets every row; `SELECT *` takes every column.
3. **One place for the connection**: the `DB` constructor stores it in a private property,
   and methods like `all()` return data instead of printing it.
4. **Do not hard code what can be a parameter**: `all('posts')`, `all('users')`.
5. **Fetch modes** decide the shape of a row: `FETCH_BOTH` (default), `FETCH_NUM`,
   `FETCH_ASSOC`, `FETCH_OBJ` (`stdClass`) and `FETCH_CLASS`.
6. **A model is a class for one row**, singular name, in `src/Models`, with a property per
   column.
7. **Deprecation warnings are a warning about the future.** Fix them now.
