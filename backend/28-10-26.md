### 1. 🧭 `AuthController`, routes and `gap`

A new controller for everything about accounts, with a method per page and per form:

```php
Route::get('/register', [AuthController::class, 'registerForm']);
Route::post('/register', [AuthController::class, 'register']);
Route::get('/login', [AuthController::class, 'loginForm']);
Route::post('/login', [AuthController::class, 'login']);
Route::get('/logout', [AuthController::class, 'logout']);
```

The same pattern as with posts: a `GET` shows the form, a `POST` to the same address
receives it. Logout is a plain `GET` link, like delete.

The header got a **Login** button next to **Sign up**. To keep them from sticking
together, Bootstrap's margin and padding utilities (`m`/`p` plus a side, like `ms-2`) would
work, but since the wrapper is already `d-flex`, the better tool is **`gap-2`** on the
parent: every child gets the same spacing, also buttons added later.

```php
<div class="col-4 d-flex justify-content-end align-items-center gap-2">
    ...
    <a class="btn btn-sm btn-outline-secondary" href="/register">Sign up</a>
    <a class="btn btn-sm btn-outline-primary" href="/login">Login</a>
</div>
```

### 2. 🍪 Cookies

The first experiment lived in `registerForm()`:

```php
setcookie('mycookie', 'tasty', time() + 60 * 60 * 24 * 30, '', '', false, true);
dump($_COOKIE);
```

The cookie only showed up in `$_COOKIE` on the **second** refresh, and the Network tab
explains why:

- `setcookie()` adds a **`Set-Cookie` response header**, just like `redirect()` adds a
  `Location` header. It asks the browser to store a key and a value.
- From then on the browser sends **all** saved cookies for the site back in a **`Cookie`
  request header**, on every request, to every page.
- **`$_COOKIE` shows what the browser sent**, not what the server just set. So the first
  response sets it, the next request brings it back.

Once stored, the server does not have to set it again: the browser keeps sending it until
it is deleted or expires.

**Expiry.** Without an expiry a cookie is a **session cookie**: it lives until the browser
is closed (all windows and tabs, not just the tab). The expiry is given as a **Unix
timestamp**, seconds since 1970; PHP's `time()` returns the current one, and letting PHP
do the arithmetic gives "30 days from now" as `time() + 60 * 60 * 24 * 30`. Because this
code sets the cookie on every visit, the expiry moves forward each time.

**HttpOnly and Secure.** JavaScript can read cookies (`document.cookie`, `cookieStore`).
The last argument, `httponly` set to `true`, hides the cookie from JavaScript. `secure`
means "only over HTTPS", which matters little on `localhost`.

**What cookies are for.** The user can read, delete and **change** them in the browser,
so a cookie is user input and must never be trusted. That rules out "user 1 is logged in"
in a cookie, but cookies are fine for harmless preferences: dark theme, chosen language,
which version of the site an A/B test showed you.

### 3. 🗄️ Sessions

`$_SESSION` does not exist until **`session_start()`** is called (before that, PHP warns
about an undefined variable). After that it is an ordinary array:

```php
session_start();
$_SESSION['bla'] = 'lol';
dump($_SESSION);
```

The interesting part: comment the assignment out, refresh, and the value is **still
there**. In the browser a new cookie appeared, **`PHPSESSID`**, with a long random string.
That string is not the data in encrypted form: changing the session data does not change
it. It is only an **id**. The data itself lives **on the server**; on Windows PHP keeps it
in files named `sess_<id>` under the user's AppData folder. Opened in an editor, such a
file shows the data **serialized**: values turned into a string together with their type
and length (`s` for string plus the character count), so PHP can turn them back into
values. Sessions can also be stored in a database.

That is why sessions are the place for login data: the browser holds only the id, and
nothing the user changes in the browser can change the values on the server.

The weak point is the id itself. Whoever has someone's session id **is** that user to the
server: copying the `PHPSESSID` value into another browser showed the same session data
there, no password needed. That is why session cookies should be HttpOnly (so a malicious
script cannot read them), why "log out and close all browser windows" used to be common
advice, and why banks ask for PIN2 before anything that matters.

### 4. 📝 Registering a user

`views/auth/register.php` started as a copy of the post create form, with the fields
changed to what the `users` table needs plus a confirmation:

```php
<form action="/register" method="POST">
    <div class="mb-3">
        <label for="name" class="form-label">Name</label>
        <input name="name" type="text" class="form-control" id="name" placeholder="Your name">
    </div>
    <div class="mb-3">
        <label for="email" class="form-label">Email</label>
        <input name="email" type="email" class="form-control" id="email" placeholder="example@mail.com">
    </div>
    <div class="mb-3">
        <label for="password" class="form-label">Password</label>
        <input name="password" type="password" class="form-control" id="password">
    </div>
    <div class="mb-3">
        <label for="password_confirm" class="form-label">Confirm Password</label>
        <input name="password_confirm" type="password" class="form-control" id="password_confirm">
    </div>
    <button class="btn btn-primary">Register</button>
</form>
```

`type="email"` gives front end validation (the browser refuses to submit something without
an `@`), `type="password"` hides the typing.

The first version of `register()` just saved a new `User`. Registering the same e-mail a
second time then crashed with an uncaught `PDOException`: *Integrity constraint violation,
duplicate entry*, because the e-mail column is unique. A `try`/`catch` around the save would
work, but it is nicer to **check first**. `find()` only searches by id, so `DB` and `Model`
got a general **`where()`**:

```php
public function where(string $table, string $class, $field, $value){
    $sql = "SELECT * FROM $table WHERE $field='$value'";
    $result = $this->conn->query($sql);
    $result->setFetchMode(PDO::FETCH_CLASS, $class);
    return $result->fetchAll();
}
```

The value is in quotes, since it may be text. And it uses `fetchAll()`: e-mail is unique,
but `where('name', ...)` could match many rows. Now `register()` sends the user back to the
form if the e-mail is taken **or** the two passwords differ:

```php
public function register() {
    $users = User::where('email', $_POST['email']);
    $user = $users[0] ?? null;
    if($user || $_POST['password'] !== $_POST['password_confirm']) {
        return redirect('/register');
    }
    $user = new User();
    $user->name = $_POST['name'];
    $user->email = $_POST['email'];
    $user->password = $_POST['password'];
    $user->save();
    redirect('/login');
}
```

`$users[0] ?? null` takes the first result or `null` if there is none. `return redirect()`
ends the method early, so no `else` is needed. There is no error message yet: landing back
on the form means something was wrong, landing on the login page means it worked.

### 5. 🔑 Logging in and out

The login form is the register form minus the name and confirmation fields, sent to
`/login`. The method looks the user up by e-mail and compares the password:

```php
public function login() {
    $users = User::where('email', $_POST['email']);
    $user = $users[0] ?? null;
    if(!$user || $_POST['password'] !== $user->password) {
        return redirect('/login');
    }
    $_SESSION['userID'] = $user->id;
    redirect('/');
}
```

"Logged in" is nothing more than **the user's id in the session**. To have the session on
every page without calling `session_start()` everywhere, it moved to the very start of
`public/index.php`, before the helpers and routes:

```php
use App\Router;
session_start();
```

Logging out removes that key; `unset()` deletes it from the array as if it had never been
there:

```php
public function logout() {
    unset($_SESSION['userID']);
    redirect('/');
}
```

(Passwords are still stored and compared as plain text here. That is one of the "deep
problems" left for a later lesson.)

### 6. 👤 `auth()` and the user dropdown

Using the `User` model inside a view would need a long `use` line, so a helper in
`helpers.php` returns the logged in user, or `false`:

```php
function auth() {
    $userID = $_SESSION['userID'] ?? false;
    if($userID) {
        return User::find($userID);
    }
    return false;
}
```

The header uses it to show either the user's name or the Sign up and Login buttons. The
name sits in a Bootstrap dropdown
(<https://getbootstrap.com/docs/5.3/components/dropdowns/#single-button>) with one item,
**Logout**:

```php
<?php if (auth()): ?>
    <div class="dropdown">
        <button class="btn btn-secondary dropdown-toggle" type="button" data-bs-toggle="dropdown" aria-expanded="false">
            <b><?= auth()->name ?></b>
        </button>
        <ul class="dropdown-menu">
            <li><a class="dropdown-item" href="/logout">Logout</a></li>
        </ul>
    </div>
<?php else: ?>
    <a class="btn btn-sm btn-outline-secondary" href="/register">Sign up</a>
    <a class="btn btn-sm btn-outline-primary" href="/login">Login</a>
<?php endif ?>
```

The `if (...):`, `else:` and `endif` form keeps the HTML readable between the PHP tags.
Logged in, the name stays in the header on every page; Logout brings the buttons back.

## ✅ Takeaways

1. **`gap-*` on a flex parent** spaces all children at once, no margins per element.
2. **`setcookie()` sends a `Set-Cookie` header; `$_COOKIE` is what the browser sends
   back**, so a new cookie appears one request later.
3. **Cookies without an expiry die with the browser**; the expiry is a Unix timestamp
   (`time()` plus seconds). `httponly` hides a cookie from JavaScript.
4. **Cookies are user input**: fine for theme or language, never for "who is logged in".
5. **Sessions keep the data on the server**; the browser only holds the `PHPSESSID`.
   Call `session_start()` once at the start of `index.php`.
6. **A stolen session id is a stolen login**, which is why session cookies should be
   HttpOnly.
7. **Check before inserting** (`where('email', ...)`) instead of letting a unique
   constraint throw an exception.
8. **Logged in = user id in `$_SESSION`**; logout is `unset()` on that key, and `auth()`
   gives the current user to any view.
