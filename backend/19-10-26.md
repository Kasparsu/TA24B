## 🗂️ Topics Covered

> 🧩 Last time ended with every table being poured into `Post`, users included. This
> session fixed that, then went one step further: an **abstract `Model`** base class that
> knows its own table, so `Post::all()` is all a controller needs. With that in place the
> first piece of an admin panel appeared: a Bootstrap table of posts with View, Edit and
> Delete buttons.

### 1. 🎯 The class becomes a parameter too

`all()` already took the table name, but the class it filled was still hard coded as
`Post`. Same fix as with the table: ask for it as a second `string` parameter and hand it
to `setFetchMode()`:

```php
public function all(string $table, string $class){
    $sql = "SELECT * FROM $table";
    $result = $this->conn->query($sql);
    $result->setFetchMode(PDO::FETCH_CLASS, $class);
    return $result->fetchAll();
}
```

The controller now got a *not enough arguments* error until it passed `Post::class` for
the posts and `User::class` for the users (PhpStorm adds the `use` import when you accept
the suggestion). The users were now real `User` objects, but with the same wall of
*dynamic property is deprecated* warnings the posts had last time. Same reason, same fix:
`User` declares a public property for every column (`name`, `email`, `password`,
`created_at`, `updated_at`), and the warnings are gone.

### 2. 🏛️ An abstract `Model` base class

It works, but every call has to know two things: the table name and the class to fill.
Not hard, but annoying and easy to get wrong. Both of them really belong to the model, so
a new file `src/Models/Model.php` became a **base class** for `Post` and `User`.

Nobody should ever do `new Model()`: it is not a post or a user, only the common part of
them. That is what **`abstract`** says. An abstract class cannot be turned into an
object; it can only be **extended**. `Post extends Model` is fine, `new Model` is an
error.

What goes into it:

- **`public $id`**: every table has an id, so it moves up from `Post` into `Model`, and the
  children inherit it.
- **`protected static $table`**: the table name. **Static** because it belongs to the class,
  not to one object (every post lives in the same table). Each child overrides it with
  its own value.
- **`public static function all()`**: creates the `DB` object itself and passes it
  **`static::$table`** and **`static::class`**. `static` means "whichever class this was
  called on", so called on `Post` it reads `'posts'` and fills `Post` objects, called on
  `User` it reads `'users'` and fills `User` objects.

```php
abstract class Model {
    protected static $table;

    public $id;

    public static function all() {
        $db = new DB();
        return $db->all(static::$table, static::class);
    }
}
```

```php
class Post extends Model {
    protected static $table = 'posts';
    
    public $title;
    public $body;
    public $created_at;
```

```php
class User extends Model {
    protected static $table = 'users';
    
    public $name;
    public $email;
    public $password;
    public $created_at;
    public $updated_at;
}
```

The controller no longer needs `DB` at all:

```php
$posts = Post::all();
```

### 3. 📄 Real posts on the blog pages

The users had only been dumped for testing, so they went away, and the home page showed
the posts from the database. Or tried to: *Cannot use object of type Post as array*.
The `posts` partial still read each post the old way, with square brackets, as the
hard-coded arrays had it. A model is an object, so the properties are read with an
arrow. There is no `date` or `author` column either, so the meta line shows
`created_at` instead:

```php
<h2 class="display-5 link-body-emphasis mb-1"><?= $post->title ?></h2>
<p class="blog-post-meta">
    <?= $post->created_at ?>
</p>
<p>
    <?= $post->body ?>
</p>
```

The **U.S.** page lost its hard-coded array of four posts too, and now also does
`Post::all()`. Everything on the public side now comes from the database.

![Arrays to objects](https://api.memegen.link/images/harold/Changed_the_posts_to_objects/Cannot_use_object_of_type_Post_as_array.png)

### 4. 🛠️ A `PostController` for the admin side

Managing posts (listing, editing, deleting) is not something the public pages should do,
so it gets its own controller, `PostController`, with an `index()` action. It starts from
`PublicController`'s code, but the view is now in its own folder, `posts`, because the
admin side will have several views per model:

```php
class PostController
{
    public function index()
    {
        $posts = Post::all();
        view('posts\index', compact('posts'));
    }

}
```

The route uses an address with a "folder" in it, `/admin/posts`:

```php
Route::get('/admin/posts', [PostController::class, 'index']);
```

The view file `views/posts/index.php` is one folder deeper than the old views, so its
includes go **one folder back** to reach the partials:

```php
<?php include __DIR__ . '/../partials/header.php'; ?>
```

To get there without typing the address, the unused **Culture** link in the navigation
was repurposed:

```php
<a class="nav-item nav-link link-body-emphasis" href="/admin/posts">Posts</a>
```

### 5. 🧭 Why links start with a slash

The new page opened, but the blog's styling was off. Every link written so far started
with a slash, except one: `blog.css` in the header. It never mattered before, because
every page was at the top level. Now it did.

- A link **with** a leading slash is an **absolute** path: it starts from the root of the
  site, so `/blog.css` is always `localhost:8000/blog.css`.
- A link **without** it is **relative** to the folder of the current address. On
  `/admin/posts`, the browser treats `admin` as a folder (it cannot know that no such
  folder exists, the router only fakes it), so `blog.css` became `/admin/blog.css`. The
  Network tab in the browser's developer tools showed exactly that request.

One slash fixes it:

```php
<link href="/blog.css" rel="stylesheet" />
```

Always start your links with a slash.

### 6. 📋 A Bootstrap table of posts

An **index** view is a **list** view. (Web servers used to show a list of a folder's
files when there was no index file in it.) For an admin page, a table fits best, and
Bootstrap makes a plain HTML table look good with a single class, `table`. The
documentation also offers:

- **`table-striped`**: every other row shaded, which makes long tables easier to read;
- **`table-hover`**: highlights the row under the mouse.

They work together, so the table got both.

A table can have up to three sections:

- **`thead`**: the column names, in `th` cells (which stand out in bold);
- **`tbody`**: the data, one `tr` row per post, made with a `foreach`, and a `td` cell per
  value;
- **`tfoot`**: optional, but on a long list it is handy to repeat the column names at the
  bottom.

Which columns? The id, the title, created and updated. Not the body: that can be a very
long text and does not belong in a table row. And one more column, **Actions**.

```php
<?php foreach ($posts as $post): ?>
    <tr>
        <td><?= $post->id ?></td>
        <td><?= $post->title ?></td>
        <td><?= $post->created_at ?></td>
        <td><?= $post->updated_at ?></td>
```

### 7. 🎨 Action buttons

There are three things to do with one post: **view** it (the full text, and whatever else
a post may have later), **edit** it and **delete** it. Bootstrap's **button group** joins
buttons into one block, and works with links as well as with buttons. If they were all
the primary blue, it would be easy to click the wrong one, so they are colour coded with
Bootstrap's colours:

- **View** is `btn-info`: you only get information;
- **Edit** is `btn-warning`: you can change something you did not mean to;
- **Delete** is `btn-danger`: the data is gone.

```php
<div class="btn-group">
    <a href="#" class="btn btn-info">View</a>
    <a href="#" class="btn btn-warning">Edit</a>
    <a href="#" class="btn btn-danger">Delete</a>
</div>
```

The fourth action does not belong to any one post: creating a new one. It went above the
table as its own button:

```php
<a href="#" class="btn btn-primary">New Post</a>
```

All the links still point to `#`. Making them actually view, edit, create and delete posts
is the work of the next lessons.

## ✅ Takeaways

1. **Pass in what varies**: `all()` takes both the table name and the class to fill.
2. **An abstract class cannot be instantiated**, only extended. `Model` holds what every
   model shares: `$id` and `all()`.
3. **Static properties belong to the class.** Each model overrides `$table`, and
   `static::$table` and `static::class` pick the class the method was called on.
4. **`Post::all()`** is all a controller needs to get every post.
5. **Models are objects**: read their properties with an arrow, not square brackets.
6. **Admin pages get their own controller**, a route like `/admin/posts` and a view folder
   per model. Includes from a subfolder go one folder back.
7. **Start links with a slash.** Without it, the path is relative to the current "folder"
   of the address.
8. **Bootstrap tables**: `table table-striped table-hover`, with `thead`, `tbody` and
   optionally `tfoot`. Leave long text like the body out of the table.
9. **Colour code the actions** in a button group: info for view, warning for edit, danger
   for delete.
