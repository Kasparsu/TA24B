### 1. 🔨 Brute force with hashcat

A hash function cannot be run backwards: there is no formula that turns an MD5 hash back
into the password. But the same input always gives the same hash, and that is enough to
crack it. **hashcat** simply tries candidates, hashes each one and compares the result
with the hash it is looking for.

`hashcat -hh` lists every hash type it supports: not only MD5 (mode 0, number zero because
it used to be so common) and its relatives, but also MySQL, PostgreSQL and Oracle password
hashes, ZIP and PDF passwords, crypto wallets, Wi-Fi passwords and more. The run in class
used:

- attack mode 3, **brute force**: try every combination;
- mode 0, **MD5**;
- a **mask** that says which characters to try: `?l` lowercase, `?u` uppercase, `?d`
  digits, `?s` symbols, `?a` all of them;
- `--increment` with a minimum of 1 and a maximum of 12, so it tries all 1 letter
  combinations, then all 2 letter ones (`aa`, `ab`, `ac` ...) and so on. For that the mask
  has to be 12 positions long.

A four letter password took about **81 million tries and less than a second**. A six
letter one, suggested by a student, took about **3 minutes**, on a school computer without a
GPU. On a machine with a graphics card the GPU does the work and it is around a hundred
times faster; several machines can split the work, or GPU power can simply be rented from
AWS, Google or Azure. Seven and eight letter passwords are within reach, which is why sites
ask for long passwords with mixed character types.

### 2. 📖 Dictionary attacks

Trying everything is not always the smartest order. People pick the same passwords, so a
**dictionary attack** tries a list of real passwords first. The classic example is
**rockyou.txt**: passwords from leaked databases (some stored in plain text, some cracked),
sorted by how common they are. It is a 14 million line, roughly 100 MB text file, which
sounds big but is nothing next to the 81 million tries of a four letter brute force. So the
usual approach is: run the word list first, brute force only if that fails. Browsing the
list is instructive in itself: `iloveyou` is number five, `rockyou` (the site the leak
came from, hence the name) number eight, and further down are names, religious words and
plenty of things not suitable for print.

### 3. 🌈 Rainbow tables, and why MD5 is out

Because MD5 always gives the same answer, there is an even faster route: people have been
computing hashes for every combination for twenty years and storing them. Searching such a
database is far faster than computing hashes again. These are **lookup tables** or
**rainbow tables**; one shown in class covers MD5 and SHA-1 and is about 190 GB, free to
download. Online lookup sites do the same: paste an MD5 hash of a common password and the
answer comes back immediately.

The second problem is speed. When MD5 came out computers were much slower, and a hash cost
noticeably more time. Today a single machine computes huge numbers of them per second, and
every few years it gets faster, so passwords would have to grow longer and longer, or the
hash function would have to be swapped every few years.

### 4. 🧂 bcrypt and the cost factor

**bcrypt** (based on the Blowfish cipher) was designed against both problems. Shown in an
online bcrypt generator:

- The **same text gives a different hash every time**, because a random part (the
  *salt*) is mixed in and stored inside the hash. So there can be no lookup table: every
  check means doing the actual work again.
- Checking is done with a separate **verify** step that takes the password and the stored
  hash and redoes the work with the stored salt.
- There is a **cost factor**, also stored inside the hash. Raising it by one doubles the
  work, so the time grows exponentially, not linearly: 12 is quick, 14 already noticeable,
  around 20 freezes the browser tab for a while. When computers get faster, the cost goes
  up instead of the algorithm being replaced.

Argon2 is a newer family that is also a good choice. Most languages and frameworks have a
library for these (on npm, search for bcrypt), and PHP has them built in.

### 5. 🔐 `password_hash()` and `password_verify()`

In `register()` the MD5 call was replaced with **`password_hash()`** and the
`PASSWORD_BCRYPT` constant (there is an Argon2 constant too):

```php
$user->password = password_hash($_POST['password'], PASSWORD_BCRYPT);
```

Since the hash is different every time, login can no longer compare two strings. It uses
**`password_verify()`** with what the user typed and the hash from the database:

```php
if(!$user || password_verify($_POST['password'], $user->password)) {
    return redirect('/login');
}
```

After deleting the old user and registering again, the `users` table showed a bcrypt hash
starting with `$2y$`. Logging in looked like it worked in class, but look closely at the
condition above: the `!` in front of `password_verify()` is missing, so a **correct**
password is sent back to the login form and a **wrong** one gets in. That bug was fixed at
the start of the next lesson.

### 6. 🌶️ More than just the password

The hash input does not have to be the password alone. Anything that can be reproduced at
login can be added: the e-mail, the user's name, or a secret value kept in the code base.
Then even a cracked weak password does not reveal a pattern, and without access to the code
an attacker cannot even start. More on that next time.

## ✅ Takeaways

1. **Never store passwords as plain text**; store a hash.
2. **A hash cannot be reversed, but it can be guessed**: hashcat hashes candidates and
   compares, and a four letter MD5 password falls in under a second.
3. **Dictionary attacks** (rockyou.txt) try real, common passwords first; long and varied
   passwords are the user's defence.
4. **MD5 is out**: rainbow tables turn cracking into a lookup, and computers keep getting
   faster.
5. **bcrypt salts every hash and has a cost factor** that can be raised as hardware gets
   faster.
6. **In PHP: `password_hash($pw, PASSWORD_BCRYPT)` to store, `password_verify($pw, $hash)`
   to check.**
7. **Check your conditions**: `password_verify()` without `!` rejects the right password
   and accepts a wrong one.
