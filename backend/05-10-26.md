## 🗂️ Topics Covered

> `include` paths again. This session fixed that for good with a `view()` helper, then
> built the first form and followed its data from the browser into PHP.

### 1. 🧰 `helpers.php`

Every time the views were included from a new place (first `index.php`, then
`routes.php`, then the controller), the `../` parts of the path had to be fixed. The
usual cure is a **helpers file**: plain functions, no class, that make common jobs in the
application easier. It lives in the project root with a lowercase name, because it is not
a class and the autoloader will not find it.

One such function already existed: `dump()`, sitting in `public/index.php` where it did
not belong. It moved into `helpers.php`, and `index.php` requires the file **before**
`routes.php`, so the routes can use the helpers too:

```php
require __DIR__ . '/../helpers.php';
require __DIR__ . '/../routes.php';
```

Delete the old `dump()` from `index.php`, or PHP complains that the function is declared
twice.

### 2. 🖼️ A `view()` function, and double quotes

The second helper loads a view by name:

```php
function view($viewName, $variables=[]){
    extract($variables);
    include __DIR__ . "/views/$viewName.php";
}
```

`helpers.php` sits next to `views/`, so the path is short and never changes again, no
matter where `view()` is called from.

The path uses **double quotes** on purpose. A quick demo with `dump()`: in single quotes,
`'$viewName'` is printed literally, dollar sign and all. In double quotes, PHP replaces the
variable with its value. The controllers now just say which view they want:

```php
view('index', compact('title', 'posts'));
```

If you did the Tech page homework, your `tech()` method can use `view()` the same way.

### 3. 📦 Scope, `compact()` and `extract()`

After the switch the pages loaded but the posts were gone, with a warning about an
undefined variable. `include` is basically copy-paste, but now the copy happens **inside
the `view()` function**, and a function is its own scope: `$posts` and `$title` from the
controller do not exist in there.

They could be passed as arguments, but different views need different data (some none at
all), so a fixed parameter list does not fit. Two built-in functions solve it, in
opposite directions:

- **`compact('title', 'posts')`** packs variables into an array. Note that it takes the
  variable **names** as strings, not the variables. The names become the keys, the values
  the values.
- **`extract($variables)`** unpacks an array back into variables named after its keys.
  The variables appear in the view even though no line of code seems to create them.

The `= []` default makes the data optional: `view('forms')` with no second argument works,
and extracting an empty array simply creates nothing. `us()` passes only `posts`, which
shows the default page title from the header partial kicking in.

Docs: <https://www.php.net/manual/en/function.compact.php> and
<https://www.php.net/manual/en/function.extract.php>

![compact and extract](https://api.memegen.link/images/handshake/compact()/extract()/Variables_crossing_a_function_scope.png)

### 4. 📝 A first form

A new route, a controller method that only shows a view, and the unused Design link in the
nav renamed to Forms:

```php
Router::addRoute('/forms', [PublicController::class, 'forms']);
```

```php
public function forms(){
    view('forms');
}
```

`views/forms.php` started as a copy of another view with the container emptied. Then the
form, piece by piece:

```html
<form action="/answer" method="POST">
    <label for="name">Name:</label>
    <input name="name" type="text" id="name" placeholder="Your name">
    <label for="age">Age:</label>
    <input name="age" type="number" id="age" placeholder="Your age">
    <input type="submit" value="Send">
    <button>Send</button>
</form>
```

- **`<input>`** is the most common field, and unusual: it has **no closing tag**, because
  it has no content. Older code often writes it self-closed as `<input />`; today that is
  not needed (and does no harm).
- **`placeholder`**: grey hint text that disappears as soon as you start typing.
- **`<label>`**: a proper caption for a field. It must be **linked** to its input to work
  properly: either wrap the input inside the label, or give the input a unique `id` and
  the label a matching `for`. Linked, clicking the label activates the field. Frameworks
  differ in which style they support, so `for` + `id` is the safer habit.
- **`type`**: `text` is the default, but `type="number"` lets the browser accept only
  numbers. Many people write `type="text"` anyway, just to make it obvious.
- **Sending**: `<input type="submit">` and a `<button>` inside the form do the same thing.
  The submit input's default text depends on the browser's language; set your own with
  `value`.
- **`name`**: the attribute that really matters. Labels, ids, placeholders and types are
  all optional for sending. A field without a `name` is not sent at all, because it has no
  name to be sent under. Name it after what it holds: `name`, `age`, maybe `size` for a
  T-shirt size.

### 5. 🔍 Query parameters and `parse_url`

The first submit (no `action`, no `method` yet) gave a **404**, on a page that definitely
exists. The address bar explains it:

```
/forms?name=Test&age=20
```

Without `method`, a form sends **GET**, and the data goes into the URL as **query
parameters**. Without `action`, it goes to the page you are on. The router compared the
whole string, `?` part included, against `/forms`.

Instead of hunting for the `?` with string functions, PHP can split a URL into its parts
(scheme, host, port, user, password, path, query, fragment):

```php
public function __construct(private $path)
{
    $this->path = parse_url($this->path, PHP_URL_PATH);
}
```

Docs and examples: <https://www.php.net/manual/en/function.parse-url.php#refsect1-function.parse-url-examples>

About the user and password parts: a URL can carry them for the server's own HTTP
authentication, the plain browser login box you sometimes see on intranets and temporary
sites. Rare today, but it is why `parse_url` knows about them.

![Query string](https://api.memegen.link/images/yuno/Router/Y_U_NO_ignore_~qname=Test.png)

### 6. 👋 Reading `$_GET`, safely

The values arrive in **`$_GET`**, a superglobal: always available, no need to pass it
anywhere. So the view can greet the visitor directly:

```php
<?php if(isset($_GET['name']) && isset($_GET['age'])): ?>
    <h1>Hello <?= $_GET['name'] ?? '' ?>! You are <?= $_GET['age'] ?? '' ?> years old!</h1>
<?php endif ?>
```

Opening `/forms` from the menu, without any parameters, produced warnings: those keys do
not exist. Two fixes, usable together:

- **`??`**, the null coalescing operator, gives a fallback when the value is missing:
  <https://www.php.net/manual/en/migration70.new-features.php#migration70.new-features.null-coalesce-op>
- **`isset()`** around the whole heading, so it only appears when both values are there.

### 7. 📮 `action`, POST and when GET is the wrong choice

**`action="/answer"`** sends the form somewhere else. That address needs a route and a
method:

```php
Router::addRoute('/answer', [PublicController::class, 'answer']);
```

```php
public function answer(){
    dump($_GET, $_POST);
}
```

Query parameters are great for **search and filters**: they stay in the URL, so the
result can be bookmarked or sent to someone. They are bad for anything **secret**: a login
with GET puts the password in the address bar, and from there into the browser history,
where anyone with the computer can open it.

**`method="POST"`** sends the data in the request body instead. The address bar shows only
`/answer`, `$_GET` is empty, and the values are in **`$_POST`**.

## ✅ Takeaways

1. **Plain helper functions go in `helpers.php`**, required before the routes.
2. **`view('name', compact(...))`** loads a view from anywhere; double quotes put
   `$viewName` into the path.
3. **A function is its own scope.** `compact()` packs variables, `extract()` unpacks them
   in the view.
4. **A field without `name` is not sent.** Link labels with `for` + `id`.
5. **GET puts data in the URL (`$_GET`)**, good for search, bad for passwords; `parse_url`
   keeps it out of routing.
6. **POST sends it in the body (`$_POST`).** Guard optional values with `??` and `isset()`.
