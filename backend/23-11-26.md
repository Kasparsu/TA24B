## 🗂️ Topics Covered

> ✍️ The Laravel blog was created last time on a different computer in another classroom,
> so this lesson started from a fresh `git clone` and went through everything needed to get
> a cloned Laravel project running: `composer install`, front end packages, a new `.env`,
> the application key, and a MariaDB database in Docker instead of SQLite. Those steps are
> exactly what a README should explain, which became the homework.

### 1. 📥 `composer install` after cloning

learnphp used to be "clone and go" because it was pure PHP. Since last week it needs
`composer install` too, and so does Laravel:

```bash
composer install
```

This creates `vendor/` with all the packages. For Laravel it takes a while: there are many
packages and the optimized autoload files are slow to generate. It has not crashed.

### 2. 🧭 Side question: other PHP frameworks

While Composer was working, a student asked about Yii. Most languages have one or two main
web frameworks: Python has Django and Flask, Ruby has Rails, Rust has Rocket, Java has
Spring Boot, backend JavaScript has a few more. PHP has many more, mostly because web
servers (and command line apps) are what it does. Laravel is the most popular.
**Symfony** matters too: it is built from reusable components, and Laravel uses quite a few
of them under the hood. Others mentioned: Yii (some nice ideas, like its active records),
CakePHP, CodeIgniter, Slim, and Phalcon, which runs its core as a C extension so less code
runs in PHP. They are all similar in many ways, and when one has a good idea, someone
makes a package that brings it to the others.

### 3. 📦 Front end packages

The PHP side is not the whole project: Vite and Tailwind come from npm, so the front end
tooling is installed with:

```bash
bun install
```

(`npm install` works just as well.) Bun wrote its own lock file, `bun.lock`, which was
committed.

### 4. 🔐 Recreating `.env`

Now `vendor/` and `node_modules/` exist, but **`.env` is missing**. As discussed last time,
it can hold secret keys, so it is in `.gitignore` and never reaches GitHub. That is what
`.env.example` is for: copy it (in the editor, or on the command line)

```bash
cp .env.example .env
```

and you get a `.env` with all the same keys. Any real secrets would be filled in from
wherever they are kept; this project has nothing that secret yet.

### 5. 🔑 The missing application key and Artisan

The server starts with `composer run dev`. With the server left running in one terminal
tab and a new tab for commands, opening <http://localhost:8000> gave a big error:
**MissingAppKeyException: No application encryption key has been specified.**

`APP_KEY` in `.env` is empty. It was generated when the project was created on the other
computer, but that `.env` stayed there. The fix comes from **Artisan**, Laravel's command
line tool. It has a lot of commands (nobody uses all of them); searching the list for
"key" finds `key:generate`:

```bash
php artisan key:generate
```

It writes a new key into `.env`. The page still showed the error until the server was
restarted, because the environment variables can be cached while it runs. Turning it off
and on again does help.

### 6. 🐬 MariaDB in Docker instead of SQLite

The next error: the database file does not exist. On creation Laravel made an SQLite file
for `DB_CONNECTION=sqlite`, and that file is not in git either. Instead of SQLite the blog
uses MariaDB, the same way learnphp did, so its Docker Compose file was copied and adapted:
the database is called `blog`, and the volume has its own name so the data stays separate
from learnphp's:

```yaml
services:
  db:
    image: mariadb
    restart: always
    environment:
      MARIADB_ROOT_PASSWORD: example
      MARIADB_DATABASE: blog
    volumes:
      - ta24bblogdbdata:/var/lib/mysql
    ports:
      - 33061:3306
volumes:
  ta24bblogdbdata:
```

With Docker Desktop running it is started in the background:

```bash
docker compose up -d
```

To see the data, a new MariaDB data source was added in the database tool: host
`localhost`, port `33061` (the port mapped above), user `root`, password `example`,
database `blog`. Test connection succeeded and the database was empty.

Laravel has a `mariadb` driver, so in `.env` the connection was changed and the commented
out lines enabled. These are local development settings, not real secrets, so the same
values were copied to `.env.example` for everyone who clones the project:

```ini
DB_CONNECTION=mariadb
DB_HOST=127.0.0.1
DB_PORT=33061
DB_DATABASE=blog
DB_USERNAME=root
DB_PASSWORD=example
```

(`127.0.0.1` is the same as `localhost`.) Then the migrations create the tables:

```bash
php artisan migrate
```

After a refresh the tables appeared in the `blog` database, and after one more server
restart (more caching) the site worked again.

### 7. 📝 README and the homework

These steps matter, and a real project will need more of them. Every project needs
documentation for them: Laravel's generated `README.md` is about Laravel, not this
project, so most or all of it can be deleted and replaced with your own:

- how to clone the project;
- what to install and in which order (`composer install`, `bun install`, `.env`, the key,
  the database, migrations);

## ✅ Takeaways

1. **After cloning a Laravel project**: `composer install`, `bun install` (or
   `npm install`), `cp .env.example .env`.
2. **`php artisan key:generate`** fixes the missing application key.
3. **Artisan** is Laravel's command line tool; search its list when you need something.
4. **Restart the server** when `.env` changes do not seem to apply.
5. **MariaDB in Docker**: own database name and volume, port `33061`, then
   `DB_CONNECTION=mariadb` and `php artisan migrate`.
6. **Development settings can go in `.env.example`**; real secrets never do.
7. **Write the README**: every step to clone, install and run the project.
