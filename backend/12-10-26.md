### 1. 🐳 A database for `learnphp`

The Docker Compose file came straight from the databases 2 repo
(<https://github.com/Kasparsu/ta24blearndb2/blob/main/docker-compose.yml>), trimmed to
only the database, with its own database name and volume:

```yaml
services:
  db:
    image: mariadb
    restart: always
    environment:
      MARIADB_ROOT_PASSWORD: example
      MARIADB_DATABASE: learnphp
    volumes:
      - ta24blearnphpdbdata:/var/lib/mysql
    ports:
      - 33061:3306
volumes:
  ta24blearnphpdbdata:
```

In DataGrip: **+ > Data Source > MariaDB**, host `localhost`, port **33061** (the outside
port), user `root`, password `example`, and the database `learnphp`, which MariaDB creates
on the very first start of the volume. Download the driver if asked, give the data source a
recognisable name, **Test Connection**, then OK. The database is there, and empty.

### 2. 🧱 The `posts` table

Built in DataGrip's table dialog, with the same decisions as in databases 2:

- **`id`**: primary key, `bigint unsigned` (more numbers than `int`, and an id is never
  negative, so unsigned doubles the range), **auto increment** so we never fill it in.
- **`title`**: `varchar(1024)`, not null.
- **`body`**: `longtext`, allowed to be null. "Body" is a common short name for the main
  content.
- **`created_at`**: `datetime` with the default expression `current_timestamp()`. Insert a
  row without it and the database writes the current time.
- **`updated_at`**: the same default, plus **on update** `current_timestamp()`, so any
  change to the row refreshes it. Equal to `created_at` means the row was never edited.

Two demo rows were added by hand (only title and body, the rest filled itself), then one
was edited: `updated_at` changed although nobody touched it.

The structure was exported with **SQL Scripts > SQL Generator** into the repo, so it can be
recreated on another computer (the data does not come along):

```sql
create table posts
(
    id         bigint unsigned auto_increment
        primary key,
    title      varchar(1024)                        not null,
    body       longtext                             null,
    created_at datetime default current_timestamp() null,
    updated_at datetime default current_timestamp() null on update current_timestamp()
);
```

### 3. 🔌 MySQLi or PDO

The connection example came from W3Schools
(<https://www.w3schools.com/php/php_mysql_connect.asp>), which is more or less fine as a
copy-paste start. PHP has two ways to talk to the database:

- **MySQLi** ("MySQL improved"), in an object oriented and a procedural style. Only MySQL,
  and MariaDB because it was forked from MySQL and is still close enough.
- **PDO** (PHP Data Objects), object oriented only. It works with about **12 different
  databases**: MySQL and MariaDB, but also SQLite, Postgres, Oracle, Microsoft SQL Server
  and others.

PDO it is: if we ever want to test with a simple SQLite file instead of a Docker setup, or
move to Postgres, the code barely changes. The example went into
`PublicController::index()`, and the hard-coded posts array went away.

### 4. 🏷️ `PDO` is not in `App\Controllers`

The first run failed: *require_once ... src/Controllers/PDO.php: Failed to open stream*.
`PDO` and `PDOException` are built into PHP, but our file starts with
`namespace App\Controllers;`, and a bare class name is looked up **in the current
namespace**. So PHP, through our autoloader, went looking for `App\Controllers\PDO`.

Two fixes:

- a leading backslash, `\PDO`, meaning the root (global) namespace. Works, but has to be
  repeated on every use, including in any code you paste in later;
- a **`use`** line at the top, once per class:

```php
use Exception;
use PDO;
use PDOException;
```

Now the editor knows what `PDO` is too, down to a link to the manual.

### 5. 🧨 Warnings, fatal errors and exceptions

PHP problems come in roughly three kinds:

- **Warnings**: something is wrong (an undefined variable, a missing array key), but PHP
  can carry on. Fix them, but the page still runs.
- **Fatal errors**: syntax errors, a failed `require`. The code stops and there is nothing
  you can do about it.
- **Exceptions**: errors the code **can react to**. A failed database connection should
  not have to be a dead white page; maybe retry, maybe show a friendly error page.

An exception is an object, so it is created with `new` and **thrown** with `throw`. The
base class every exception extends is `Exception`, and it takes a message. A demo
`throw new Exception(...)` in the method made VS Code grey out every line below it:
*unreachable code*. A throw ends the function like `return` does, but it keeps going: the
calling function ends too, and its caller, until something **catches** it. If nothing
does, it becomes *Fatal error: Uncaught exception*.

Catching uses `try` and `catch`: run the risky code in `try`, and say in `catch` which
exception type you handle and what to do instead. After the catch the rest of the code runs
normally. The catch does not have to be in the same function; it can be anywhere further
up the call chain.

That is exactly what the PDO example does. `new PDO(...)` **throws `PDOException`** if the
connection fails, and `ERRMODE_EXCEPTION` makes later database errors throw too. If the
connection throws, execution jumps straight to `catch`, so "Connected successfully" is
never printed. A bit like an `if`:

```php
try {
    $conn = new PDO("mysql:host=$servername;dbname=$dbname", $username, $password);
    // set the PDO error mode to exception
    $conn->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
    echo "Connected successfully";
} catch (PDOException $e) {
    echo "Connection failed: " . $e->getMessage();
}
```

### 6. 💿 "Could not find driver", and a short history of drivers

The catch worked: *Connection failed: could not find driver*. PHP, like DataGrip earlier,
needs a **driver** for the database, and the PHP install does not enable it by default.
Drivers are separate so they can be updated on their own.

A side story for the gamers who install graphics drivers: up to about Windows 7, a new PC
came with a stack of driver CDs. Often the network driver was missing too, so the PC could
not go online to download the network driver. You fetched it on another computer and
carried it over on a flash drive.

### 7. ⚙️ `php.ini` and extensions

PHP's settings live in **`php.ini`**. On Windows (installed with Winget) there is none at
first:

1. `php --ini` shows *Loaded Configuration File: (none)*.
2. `where php` shows the install folder. Copy the folder path (without `php.exe`) into File
   Explorer.
3. Turn on **View > Show > File name extensions**, otherwise some files show extensions and
   some do not.
4. Copy `php.ini-development` (keep the original as a fresh backup) and rename the copy to
   **`php.ini`**. Windows warns about changing the extension; yes, we know.
5. `php --ini` again: now it lists the file.

Open it in an editor with line numbers (VS Code, Notepad++). Comments start with `;`. It
sets error display, memory limit, upload size and much more. Around line 920 is the list
of extensions, all commented out.

Why not enable them all? PHP starts from scratch for **every request** and loads every
enabled extension each time, used or not. Extensions are written in C and very fast when
you need them, but each unused one costs memory and time on every page. Enable only what
you use.

What we need: **`pdo_mysql`** (there is no separate MariaDB one; MySQL's works). Remove
the `;` in front. On Windows also uncomment the **`extension_dir`** line that points to `ext`
(around line 758), because Winget does not install PHP into `C:\php`, where it looks by default. Save, and
**restart the PHP server**: code changes are picked up live, `php.ini` changes are not.

![Extensions](https://api.memegen.link/images/jw/Uncomment_every_extension_in_php.ini/Probably_not_a_good_idea.png)

### 8. ✅ Connected

Next error: *No connection could be made because the target machine actively refused
it*. Progress. The example's connection details were placeholders, so they became ours:
host with the outside port, our user, password and database:

```php
$servername = "localhost:33061";
$username = "root";
$password = "example";
$dbname = "learnphp";
```

*Connected successfully.* Committing on a classroom computer for the first time also
needed `git config --global user.name` and `user.email`, and a browser login to GitHub.

## ✅ Takeaways

1. **One Compose file per project**, with its own database name and volume; connect
   DataGrip on the outside port.
2. **Let the database fill `id`, `created_at` and `updated_at`**, and export the table as SQL.
3. **PDO over MySQLi**: one API for many databases.
4. **Built-in classes live in the root namespace.** `use PDO;` at the top of a namespaced file.
5. **Exceptions can be caught**: `throw` ends functions up the chain until a `try`/`catch`
   handles it; uncaught, it is a fatal error.
6. **Create `php.ini` from `php.ini-development`**, enable only the extensions you need
   (`pdo_mysql`, plus `extension_dir` on Windows), and restart the server.
