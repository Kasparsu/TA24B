### 1. 🐳 A fresh database from Docker Compose

```yaml
db:
  image: mariadb
  environment:
    MARIADB_ROOT_PASSWORD: example
    MARIADB_DATABASE: project     # created automatically on the first start
  ports:
    - 33061:3306
```

`MARIADB_DATABASE` only runs when the volume is created. To start from scratch:

```bash
docker compose down -v    # -v also removes the named volumes: ALL data is gone
docker compose up -d
```

Then add the data source in DataGrip (MariaDB, port 33061, `root` / `example`) and the
`project` schema is already there, empty.

> ⚠️ If your volume already existed, there is no `project` database. Do not type `project`
> into the data source's database field, or every query fails with *Unknown database
> 'project'*. Use the schema you actually have.

### 2. 🏷️ Naming tables and columns

- **lowercase, words separated by `_`**: `users`, `birth_date`, `created_at`. Depending on
  the database and its settings, names can be case sensitive, so `Users` and `users` could
  be two different tables. Pick one style and never mix.
- **Tables are plural** (`users`), because a table holds many rows. One row is one user.
- Frameworks and ORMs often have their own conventions and may name things for you. If the
  framework decides, going against it means extra code.

### 3. 🔑 The `id` column

Almost every table should have one:

- **primary key**: unique, and the table is ordered by it
- **auto_increment**: the database fills it in, 1, 2, 3, ...
- **`bigint unsigned`**: why not plain `int`?

The integer types differ in bytes: `tinyint` 1, `smallint` 2, `mediumint` 3, `int` 4,
`bigint` 8. A signed `int` tops out around 2 billion. There are 8 billion people, plus
forgotten second accounts, bots and AI agents. `bigint` removes the ceiling.

**Signed vs unsigned**: binary has no minus sign, so a signed number spends one bit on
"negative or positive". An id is never negative, so `unsigned` gives that bit back and
doubles the positive range.

### 4. 📅 Data types that fit the data

| Column | Type | Why |
|---|---|---|
| `name` | `varchar(1024)` | No `string` in SQL. `varchar` with a generous max, because real names can be absurdly long. |
| `birth_date` | `date`, nullable | **Not age.** Age changes every year, birth date never does. Calculate the age when you show it. |
| `email` | `varchar(254)`, **unique**, not null | 254 is the real maximum length of an email address (RFC 5321). Unique, because it is the login. |
| `password` | `varchar(2048)`, not null, **not unique** | A "password already taken" error would tell an attacker that someone uses it. Passwords are stored hashed, more on that in learnphp. |
| `created_at` | `datetime`, default `current_timestamp()` | Filled in by the database when the row is made. |
| `updated_at` | `datetime`, default `current_timestamp()`, `on update current_timestamp()` | Refreshed by the database on every change. |

`created_at` and `updated_at` are worth adding even before you need them, because the day
you do need them, the old rows already have values.

Dates in the database are stored in UTC (+0). Estonia is +3 in summer, which is why a row
created at 14:18 showed 11:18. Convert for display, in the browser or on the server, but
keep the stored data in UTC.

**`null` or `not null` is a design decision.** Is a birth date required? It depends on the
project. If you allow `null`, every piece of code that reads that column has to handle the
missing value.

A side trip on `timestamp`: it counts seconds from 1970, and where that count is a signed
32-bit number it overflows in **January 2038** and jumps back to 1901. Modern systems are
fine, but plenty of old embedded hardware, network gear and infrastructure is not.

### 5. 🔗 Foreign keys, and what happens on delete

A `posts` table needs to say who wrote the post. Not the author's name or email (those are
already in `users`) but the smallest possible reference: `user_id`, with **the same type
as `users.id`** (`bigint unsigned`). A smaller type could fail to hold some user's id.

A plain `user_id` column accepts any number, including users that do not exist. A
**foreign key** makes the database check it:

```sql
constraint posts_users_id_fk
    foreign key (user_id) references users (id)
        on delete cascade
```

It protects both directions:

- You cannot insert a post with `user_id = 5` if there is no user 5.
- You cannot delete a user and leave their posts pointing at nobody. What happens instead
  is your choice:

| `on delete` | Effect |
|---|---|
| `no action` / `restrict` | Deleting a user with posts is refused. Delete the posts first. |
| `cascade` | Deleting the user deletes their posts too, like dominoes. |
| `set null` | Posts stay, `user_id` becomes `null` (the column must allow `null`). Reddit and Discord do this: "[deleted]". |
| `set default` | Posts move to a default user, e.g. a "Deleted user" row. |

No option is right in general. It depends on what the application needs, and sometimes
on the law, since a deleted user's personal data usually has to go.

### 6. 🖱️ Building tables in DataGrip, and getting the SQL out

- **New table**: right-click the schema > New > Table. Add columns; the `...` next to a
  column name has *make primary key* / *unique key*.
- **Foreign keys**: the *foreign keys* folder in the same dialog, `+`, choose the target
  table and column.
- The SQL shown in the dialog is **only a preview**. Editing it there does not change the
  table. If it shows leftovers like `unknown null`, fix the column types above it.
- **Export the SQL**: right-click the schema > **SQL Scripts > SQL Generator** (or
  **Generate DDL to Clipboard**). Save it as `project.sql`.
- **Rebuild from the file** on a new machine or after a mistake: SQL Scripts > Run SQL
  Script. Structure comes back, data does not.

The resulting file is in the repo:

```sql
create table users (
    id         bigint unsigned auto_increment primary key,
    name       varchar(1024) not null,
    birth_date date null,
    email      varchar(254) not null,
    password   varchar(2048) not null,
    created_at datetime default current_timestamp() not null,
    updated_at datetime default current_timestamp() not null on update current_timestamp(),
    constraint users_pk_2 unique (email)
);
```

### 7. 🗺️ Diagrams

Right-click the schema > **Diagrams > Show Diagram**. Tables, columns, types, and a line
for every foreign key. Layout can be moved by hand or re-applied automatically. To get an
image: right-click the diagram > **Export Diagram > Export to Image** (or copy it to the
clipboard).

If two tables that belong together have no line between them, the foreign key is missing.

## ✅ Takeaways

1. **lowercase, `snake_case`, plural** table names.
2. **`id bigint unsigned auto_increment primary key`** on almost every table.
3. **Store facts that don't change**: a birth date, not an age.
4. **`null` vs `not null` and unique vs not** are design decisions, not defaults.
5. **Foreign keys** keep references real. Choose deliberately what `on delete` does.
6. **Let the tool write the SQL**, but you make the decisions. Export it, and generate the
   diagram to check your connections.
