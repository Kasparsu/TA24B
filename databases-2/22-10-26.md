### 2. 🐛 Review issues in your project repos

Before the lesson every cinema project in the school's GitHub organisation was gone
through, and the findings were posted as **GitHub issues** in each repo: bugs and
enhancements. Some housekeeping came up on the way: one team repo was private and had an
unexpected number, and one project lived in a **fork**, where issues are switched off, so
the review could not be posted there.

What to do with the issues:

- **Read each one and decide** whether it is a valid concern. Is it a real problem, or
  not a problem in your case?
- If it is real, **fix it and close it**. Assign issues to each other, so the work is
  shared across the team.
- If it is not a problem, **write a short explanation and close it**.

Everybody has issues. That does not mean your code is bad (or, well, it is, but that is
fine): nobody's code is perfect, the teacher's demos included. The review was not written
by hand line by line either, so not every point is guaranteed to be right, which is
exactly why you check, answer and decide. Making mistakes is how you learn; fixing them is
the next step.

### 3. 🧩 Consultation: a thousand lines in `App.vue`

A student asked about an issue that said the club application form was never shown,
although clicking the button did open it. Fine: if it works, write that in the issue and
close it.

The bigger problem in that project was the structure. The app already used **Vue Router**,
but almost everything still went through `App.vue`, which had grown to around a thousand
lines. The main reason to use Vue (or any component framework) is to **split code into
small files**:

- Let the router do the routing: one view file per page, so you can see which links exist
  and where they lead.
- Keep `App.vue` as the container (layout and `<router-view>`), not the place where every
  page lives.
- **If you have to scroll a lot to find something, you are doing it wrong.** Code should
  be easy to find.

The part was written by another team member, so the advice was: tell them, and let them
fix it. You are all students; mistakes are fine, but try to do better.

### 4. 🔓 A hidden button is not a locked door

Another issue in the same project: in build (production) mode the edit buttons for movies
and banners disappear, so the student thought users could not edit anything. But the issue
was about the **backend**, not the UI.

The edit buttons only send requests (`POST`, `PUT`, `PATCH`). If the endpoints behind
them still accept those requests, anyone who knows what they are doing can send the same
request themselves, from any tool, without the nice form. Hiding the button disables the
edit UI, not the edit functionality. The check has to be on the server: the endpoint
itself must refuse requests that are not allowed.

### 5. ⌚ Side trip: calls and notifications over Wi-Fi

A student mentioned making phone calls from a computer through a linked phone. Not that
crazy: on Wi-Fi a phone routes calls over the internet anyway. A related surprise: a
smartwatch kept getting notifications while the phone was in another house, far beyond
Bluetooth range. The phone had synced the saved Wi-Fi passwords to the watch, so the
watch joined the Wi-Fi itself and talked to the phone over the network. Convenient, and a
reminder that devices do things you never told them to.

## ✅ Takeaways

1. **Every review issue gets an answer**: fix it and close it, or explain why it is not a
   problem and close it.
2. **Share the fixes**: assign issues to each other so the whole team works on them.
3. **Split your frontend into small files.** Let the router route and keep `App.vue` a
   container. Too much scrolling means the structure is wrong.
4. **Hiding a button is not security.** The backend endpoint must refuse what the user is
   not allowed to do.
5. **Use the week after the period** to fix grades and finish missing work.
