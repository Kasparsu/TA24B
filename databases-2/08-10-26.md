### 1. 💣 Side trip: `rm -rf` and the stray space

A question at the start: what happens if you type `rm -rf` in Git Bash? With nothing after
it, nothing at all: `rm` needs a file or folder to delete.

The famous "delete the whole system" version targets the root folder `/`. On Linux that
is refused unless you add `--no-preserve-root`, so nobody does it by accident. The real
danger is a **typo in a legitimate command**:

- You paste a full path to delete one folder, but a space sneaks in after the first `/`.
  Now the command gets two targets: the root folder, and a folder that does not exist.
- You want to delete all images with `*.png`, but type `* .png`. The `*` alone means
  *everything in this folder*, with none of the root folder's protection.

In Git Bash on Windows the fake root still maps to real drives, so a mistake can reach
your user folder, downloads and projects long before Windows itself breaks. Every time you
write `rm -rf`, read the command twice. If you are unsure, try it in a Docker container or
a virtual machine first.

### 2. 🎬 A movies table with a million rows

To have something slow to measure, a throwaway Laravel project was set up against the
MariaDB container (Laravel itself comes later in the server side course; here it was only
a quick way to get an ORM). A new schema was made for it in DataGrip, and the migration
created the tables.

The class listed the fields their cinema projects had for movies: title, description,
director, release date (a date, or a date and time when the time matters), language,
and in the chat also length and rating. The same pieces as in your own task:

- **Migration**: the movies table with those columns.
- **Factory**: how to make *one* fake movie. Faker gives a sentence for the title, a
  paragraph for the description, a name for the director, a random date between 30 years
  ago and now for the release date, and a language code.
- **Seeder**: runs the factory many times.

The goal was a **million** movies. Creating them all at once would build a million objects
in memory before anything reaches the database, so the seeder ran **1000 batches of 1000**
instead. That takes a while, so it kept filling the table in the background during the
next parts.

### 3. 🔎 Indexes: the same query, three times faster

What does a cinema site actually ask for? Not "all the movies", but things like *the
movies released this past month*, maybe 20 of them. That query was run on the table
(around half a million rows by then): about **28 ms**.

Then one change: an **index** on the release date column. The same query: about **9 ms**.

A few milliseconds sound like nothing, but:

- One page load can need many queries (the movies, then everything connected to them).
- On a development machine you are the only user. With thousands of people querying at
  once, every request slows down, and 28 ms can turn into seconds.

**What an index does:** the table is kept in primary key (`id`) order. An index makes the
database keep one more sorted list, by that column, so searching or sorting by it no
longer means scanning every row. The price: every **insert gets slower**, because the
extra list has to be updated too. Primary keys and unique keys are indexes as well, in the
background.

The index can also be declared in the ORM's migration instead of clicking it in DataGrip.

**Where to put indexes:** look at the `where` (and sort) parts of your queries. Do you show
the latest movies? Index the release date. Can users search by title, description or
director? Do you filter by length or rating? Those are candidates, but only if the search
is actually used often enough to pay for the slower inserts.

![Index](https://api.memegen.link/images/stonks/One_index_on_the_release_date/28_ms_down_to_9_ms.png)

### 4. 🗃️ Caching: do not ask the same question twice

Even a fast query costs something, and the bigger the database, the more. The system you
build might still be running ten years from now with far more data, and nobody will know
why it got slow. So think ahead: does the answer change every time? *The latest movies*
is the same answer for everyone for hours. Ask the database **once, store the answer**,
and give the stored answer to the next visitor. That is **caching**.

But new movies come out, so the cache must not live forever. You choose how long:

- **Even one second can matter.** With a million visitors per second (think Netflix or
  Facebook), a one second cache turns a million identical queries into one, and nobody
  notices data being a second old.
- With few users and data that rarely changes, cache much longer. Today's screenings do
  not change during the day, so they can be cached until the day ends.
- **Invalidation**: when an admin adds a news article, the cached list is thrown away, and
  the next visitor triggers a real query that refills it.

Where to keep the cache: in **files** (the simplest), in a **database table** (what Laravel
does by default), or in a dedicated store like **Redis** or Memcached. Laravel's config
lists all of these, including an array store and a failover option, and switching is a
setting, not a rewrite.

Caching is not new for this class: last year's web scraper stored every downloaded page,
so a mistake did not mean fetching the whole site again. Browser caching is yet another
topic.

### 5. 🟥 Redis: a key value store in memory

<https://redis.io/> was shared at the start of the lesson. Redis was added to the lesson's
Docker Compose file from the official image on Docker Hub, with its port **6379**, and the
Adminer service was removed (DataGrip already does that job). DataGrip connects to Redis
like to any other data source: localhost, port 6379, user `root` with an empty password
worked after the driver download.

Redis is a **NoSQL key value store**. No tables, no columns, no schema: you set a key to a
value and read it back, much like a JavaScript object or an associative array in PHP. It
has numbered databases (0 to 15) instead of named schemas, and some more advanced data
types, but key and value is the core.

Why use it next to a relational database?

- **Everything is in memory** while Redis runs. MariaDB or Postgres keep some data in
  memory but write to disk and read from it; memory is much faster. Simple commands came
  back in 4 to 6 ms.
- **It is simple**: no query planning, no joins, no table structure to work out.

That makes it ideal for caches. The bigger point: **a system does not have to use only
one database**. During development one database keeps things simple, but choose tools that
let you swap. In Laravel the main database can be SQLite, MySQL, MariaDB or Postgres,
sessions and cache can each live somewhere else, and changing that is configuration.

![Redis](https://api.memegen.link/images/both/SQL_database_or_Redis~q/Why_not_both~q.png)

### 6. 🧮 ORMs are convenient, not always efficient

ORMs are the recommended way to query, especially for simple queries. But even simple
queries can come out inefficient, and sometimes writing the SQL yourself is better. Once
your project has real pages, check **how many queries each page load makes** and how long
they take, and optimise the worst ones.

The task for the rest of the lesson, using the structure you already designed:

1. **Indexes**: which fields will you search, filter or sort by (release date, title,
   description, director, length, rating)? Which of them deserve an index?
2. **Caching**: which answers can be stored, and for how long, while staying up to date

Optionally try Redis or a caching library for your language (C#, Go, Java, PHP, JavaScript
all have them). Prefer one that can start with the database you already use and later

## ✅ Takeaways

1. **Read every `rm -rf` twice.** A stray space turns one folder into everything.
2. **Seed big tables in batches**, not a million objects in memory at once.
3. **An index keeps an extra sorted list**: faster searches by that column, slower inserts.
4. **Index what you search, filter and sort by**, if it is used often enough to be worth it.
5. **Cache answers that do not change every time**, for as long as they stay true, and
   invalidate when the data changes.
6. **Redis is an in-memory key value store**, fast and simple, ideal for caching next to
   a relational database.
7. **ORMs can make slow queries.** Count the queries per page and fix the expensive ones.
